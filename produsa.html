Produsa

Turning a website build into a conversation.

Product Designer and Builder · Produsa Labs · Feb to Oct 2026

Overview

An agent interviews the owner the way a developer would scope a project, then builds the site.

Produsa builds a full website through a conversation. The agent reads the brand from references, builds the site, and lets the owner refine it by chatting. It works in a web studio and over a messaging app, in multiple languages.

Produsa launched in August 2026. I worked on it from February, through launch, until October.

[ IMAGE: the studio, chat on the left, the live site building in the centre ]

The problem

For a small business owner in a tier-2 or tier-3 Indian city, a good website is out of reach.

AgenciesDrag-and-drop builders
Expensive quotes and weeks of back-and-forth Expect the user to know what a hero section or a grid is
Technical vocabulary the owner does not speak English-first interfaces
A site the owner cannot edit afterwards The owner still makes every design decision alone

The people we designed for run a bakery, a bearings distributor, a cafe. Most are not fluent in English, design or development language.

The thesis: if the whole build is done by agents, the cost of a good website falls and the quality holds.

Problem statement How might we let a non-technical owner build and edit a real website by talking, and trust what the system tells them?

Research

Almost every failure traced back to one pattern, which we named false confirmation.

Vocabulary. Owners could not answer "pick a type scale", but they could answer "who is this for?" and "show me two sites you like". Discovery had to match their mental model, so it asks about intent, and the agent translates that into design decisions.

Alpha user test. Before the August launch we ran a structured usability test with four real business owners: a steel trader, a bearings distributor, a cat cafe and a boutique bakery. Discovery tested well. When we synthesised the findings, the failures converged on the system saying something was true when it was not.

The chat said "done" to edits it never applied, for most of the owners. It invented clients, prices and testimonials, even when the brief said not to. A build that had died kept animating its progress bar into the high nineties. One owner asked for a cart and checkout on a static site, and the system added buttons that did nothing, then said the cart would "switch on when you ship it for real".

The turning point

Reading the full transcripts instead of the summaries.

One bakery owner uploaded her photos and was told "done" three times before they actually appeared. The fix was not a smarter agent. It was an honest one.

The system

A set of specialist agents, each with one job and a defined handoff.

Research, art direction, content, build, then a QA pass. When quality drops, the team can see which stage failed.

At my studio, Bleed and Margins, I had led a team through website projects for D2C brands, and every project ran the same way: research the brand, study the competitors, set the creative direction, write the content, build, then review. So the agent structure came naturally. Each step became a specialist agent with its own skill file and handoff. Designing the pipeline mostly meant writing down a process I already ran with people.

On high-stakes calls, like art direction and whether a brief is feasible, agents debate a position against a critique. I designed that debate so disagreement is cheap and the losing argument is logged. Debate costs time and tokens, so it only runs on the few decisions that change the outcome.

The user never sees any of this. Internal states collapse into one plain message: still working.

Key decisions

Four calls that decide whether a person can trust the machine.

01

"Done" only when it is done.

What happened

The chat used to decide it had succeeded based on what the model said, or because a version got saved.

The decision

I moved success checks to the result, so the assistant's confidence matches what actually happened. The reply can only claim a change if the page itself changed. For images, the system checks that the image data is embedded on the page, not just that an upload tool ran.

The trade-off Sometimes the chat now says "I could not apply that" where it used to say "done". That reads as a weaker assistant for one message. This single change fixed false confirmation.

What we shipped[ DRAWING: the chat admitting it could not apply the edit, owner mildly annoyed but informed ]

Trade-off plate 01. The confident lie, beside the useful admission.

02

Say what a static site cannot do.

What happened

A finished Produsa site is static. It cannot run a cart, checkout, payments or logins. The system was promising all four.

The decision

The agent refuses those requests plainly and offers what works instead: an order-by-message button on each product, or a quote button that opens the enquiry form with the item filled in. I also found the "switches on when you ship" promise written into the system prompt itself, and removed it everywhere.

The trade-off Saying "I cannot build a live checkout" can lose a sale in the moment. A dead button costs more later.
03

Progress that cannot lie.

What happened

A build takes minutes. An earlier version once froze at 20% for 15 minutes while the build ran fine underneath it.

The decision

The narration can be dramatic, but system status has to be accurate. Progress stops at 90 to 95% until the build is finished, so it never looks done while it is stuck. When the system needs the user, every agent card switches to "Waiting for input". The wait has four layers: a pulse before the first event, narration paced to the median build time with a real clock, a panel showing elapsed time and finished agents, and a live scene that falls back to that panel if it fails to load.

Progress survives a refresh, a reconnect or a missed event. Loading, waiting and error states were each designed as their own screens, and the chat is never silent. If a provider key runs out of credits, the build switches to the next valid one. A lapsed site is paused, never deleted.

The trade-off Real progress moves in uneven jumps, and "still working" is less comforting than a fake 92%. The user test showed the fake version is what loses trust.

Trade-off plate 02. Invent the story, never invent the state.

04

The whole build over chat, in the user's language.

What happened

The owners we designed for already live inside a messaging app, and most of them do not work in English.

The decision

The full pipeline runs inside that messaging app, in multiple languages. A shop owner can scope, build and edit a real website without installing anything or using English. For these users, the chat is the product.

The trade-off A chat thread is a smaller canvas than the studio, and output quality still varies by language. We accepted that to remove the two biggest barriers: an app to learn and a language to speak.

Other decisions

Six smaller calls, each with a cost.

A discovery interview before the build. A few intent questions, then the owner picks an art direction, and the agent makes the design decisions after that. More steps than a single prompt box, accepted because an unscoped prompt produces a generic site.

The centre panel is always the website. Research streams in, then a live clickable site, then an updating overlay during edits, then a live URL. The render pipeline has to be fast and cannot break, which moved real engineering work downstream.

Reference-grounded builds. The agent builds from the owner's own material and sites they like, so a bearings distributor and a cat cafe look like different companies. A weak reference gives a weak build, so I built a curated library across niches to keep the floor high.

Editing by chat. After the first build, owners refine by talking. Most of my conversational UX work lived here, especially intent resolution: the model gets an exact map of the current page, so each instruction lands on a real section. Plain language is easy for the owner and hard for the system.

Behavioural checks as a gate. Every generated screen, and Produsa's own interface, is checked against written rules: smart defaults, a live prototype before any signup wall, the user's idea carried through signup, no hard blocks mid-edit, no fake urgency. A failed check gets one mandatory revision. It slows down shipping a good-looking screen, which is how dark patterns stay out.

Pricing

One wallet, one balance, no fake discounts.

One wallet. Building, editing and keeping a site live all draw from the same credits, so owners deal with one balance instead of separate bills.

Monthly plans. Each plan gives a monthly credit allotment, so owners can keep editing without counting every change. Top-ups refill it.

Clarity. A plain "where your credits go" view, and a free entry window so owners see value before the paywall.

No fake discounts. I pulled the strike-through "was" prices from the pricing page, because those prices never existed.

What we refused

Each of these was considered, and most were partly built before we cut them.

What we cutWhy it was temptingWhy it wentWhat we did instead
[ 1 ]Heavy animation and 3D cards on generated sites Looks impressive in a demo Every site started to look like the same template Light CSS reveals on scroll
[ 2 ]"Built in 30 seconds" in marketing A strong ad hook A real build takes minutes. False speed breaks trust and risks ad-policy rejection Marketing states the real build time
[ 3 ]App, dashboard and API claims Makes the product sound bigger Produsa builds websites. Owners would sign up for things it cannot do Copy rewritten to match what the product does
[ 4 ]Rupee prices on the build button Feels transparent Money at the point of action makes owners hesitate on every build Credits on the button, rupee comparison in the wallet
[ 5 ]Silently swapping in a generated image Keeps the build from failing when a photo cannot be used The owner believes it is their photo. False confirmation again The agent says the photo could not be used
[ 6 ]Greeting owners by first name Feels personal A third of stored names are not first names, so many greetings would be wrong A plain "Hey"

Outcome

600+ sites built in the first two months after launch, with paying users.

False confirmation was closed at the source, with a regression test for each case from the user test. Honest refusals replaced the dead commerce buttons. The full build and edit flow runs over chat, in multiple languages.

How I used AI

The prompt was a design surface.

Produsa runs on frontier Claude models, with multi-model routing that sends some tasks to Kimi. I used Codex for development tasks, running parallel agent sessions to build my parts of the system.

I wrote the skill files that define what each agent can do, and set up the web-designer agent to study core design principles before it builds. The agent's voice, its refusals and its grounding rules were written together with the interface, and the output schema was treated as part of the UX.

Reflection

What I would carry forward.

Honesty is not enough on its own. Users want stores, and a static site cannot be one. The guardrail is a bridge until the product can actually do commerce.

Models default to saying yes. Honesty had to be engineered in against that, and it needs tests to stay in place. Next time I would build the structural checks earlier.

Language quality is uneven. Reaching tier-2 and tier-3 users in their own language is the point, and output quality still varies by language. Closing that gap matters more than polishing the English experience.
